# web — aws-cost-playground

SPA em React 19 + TypeScript + Vite. Stack e decisões: `docs/architecture/aws-cost-playground/ADR-0001-stack.md`.

## Pré-requisitos

- Node 26 (veja `.nvmrc`; com nvm: `nvm use`).
- npm. O `.npmrc` fixa versões exatas (`save-exact`) e exige 7 dias de idade mínima nos pacotes (`min-release-age=7`).

## Uso

```bash
npm ci        # instala conforme o package-lock.json
npm run dev   # servidor de desenvolvimento do Vite
```

## Qualidade

```bash
npx prettier --check . && npx eslint . && npx tsc --noEmit && npm test -- --run && npm run build
```

### Lint de arquitetura

As regras de import do ADR-0001 são verificadas pelo `npx eslint .` (config em `eslint.config.js`) e pelo teste `src/architecture.test.ts`:

- Uma feature só importa outra feature pelo `index.ts` dela.
- `app/` e as features podem importar `shared/`; `shared/` não importa feature nem `app/`.
- `**/application/**`, `**/model/**`, `src/shared/lib/design/**`, `src/shared/lib/api/**` (exceto `ApiProvider.tsx`, o único módulo com React) e `src/shared/lib/money.ts` não importam `react`, `react-dom`, `@xyflow/*`, `@tanstack/*`, `zustand` (nem `zustand/*`) nem módulo `http` (padrão `**/http`, que inclui `shared/lib/http`). O motor de preço, o contrato do design, as portas da API e o dinheiro ficam em TypeScript puro.

## Configuração de runtime (`/config.json`)

O build é o mesmo em todos os ambientes. O que muda por ambiente é o arquivo `/config.json`, buscado na inicialização (sem cache) e validado com zod. O deploy sobrescreve o arquivo de cada ambiente; `public/config.json` traz só valores de desenvolvimento.

```json
{
  "apiBaseUrl": "https://api.example.com",
  "cognitoAuthority": "https://cognito-idp.us-east-1.amazonaws.com/<pool-id>",
  "cognitoClientId": "<client-id>"
}
```

| Campo              | Regra                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------ |
| `apiBaseUrl`       | URL da API; `https`, ou `http` apenas em `localhost`/`127.0.0.1`; sem credenciais, query nem fragmento |
| `cognitoAuthority` | URL do emissor OIDC do Cognito; mesma regra de URL                                                     |
| `cognitoClientId`  | 1 a 128 caracteres: letras, números, `_` e `-`                                                         |

Se o arquivo faltar, não for JSON ou violar o schema, o app mostra uma tela de erro e não carrega. Não coloque segredos nele: é público.

## SEO e arquivos públicos

- `index.html` traz título, descrição, `theme-color` (claro e escuro), Open Graph, Twitter Card e favicon (`public/favicon.svg`). Sem `og:image` (o cartão é `summary`) e sem JSON-LD (a #70 não pede; um `<script type="application/ld+json">` gerado no build é bloco de dados e passaria pela CSP).
- `VITE_SITE_URL` (origem https, sem caminho, como `https://exemplo.com`) é lida no **build**. Com ela, a página ganha `canonical` e `og:url`, e saem as URLs do `sitemap.xml` e a linha `Sitemap:` do `robots.txt`; sem ela, esses itens ficam de fora e o build avisa. Valor inválido derruba o build. O pipeline de deploy (#22) precisa defini-la por ambiente; não há padrão.
- `tooling/seo.ts` é a fonte única das rotas: `PAGE_META` (título e descrição de `/privacidade` e `/termos`; `/` usa os do `index.html`), `PUBLIC_ROUTES` (`/` mais as de `PAGE_META`: as únicas indexáveis, que formam o `sitemap.xml`). O plugin gera `robots.txt` e `sitemap.xml` e injeta no fim do `<head>` o bloco `<script type="application/json" id="seo-routes">` (rotas e origem) e, depois dele, `<script src="/seo.js">`. A ordem importa: `seo.js` roda ao ser lido. O bloco JSON não é executado, então a CSP não o barra.
- `public/seo.js` (clássico, como `theme.js`) lê o bloco no carregamento. O HTML é o mesmo para toda rota da SPA, por isso canonical e `og:url` nunca vêm nele: um canonical fixo diria que toda rota é cópia de `/`. Rota pública: canonical e `og:url` do caminho, mais título, descrição, `og:*` e `twitter:*` próprios quando a rota está em `PAGE_META`. Qualquer outra rota leva `noindex`, sem canonical: as privadas (`/designs`, `/conta`, `/auth/callback`), `/comparar` e caminhos inexistentes, que o CloudFront responde com o `index.html` e status 200 (sem o `noindex`, seriam soft 404 duplicando a inicial). Não há `Disallow` no `robots.txt` de propósito, para o rastreador abrir essas rotas e ver o `noindex`.
- Limitações: (1) tudo isso depende de JS. O Google renderiza JS; rastreador sem JS (e prévia de link em rede social) vê os metadados da inicial, sem canonical nem `noindex`. A alternativa sem JS é `X-Robots-Tag` no CloudFront (`infra/`). (2) Roda só no carregamento: na navegação dentro da SPA, título e canonical não mudam (o rastreador abre cada URL do zero). Rota pública nova entra em `PAGE_META`; fora dele, a rota nasce com `noindex`.

## Estrutura

- `src/app/` — composition root: bootstrap (carga da config e providers) e rotas (`/`, `/designs`, `/comparar`, `/conta`, `/privacidade`, `/termos`, `/auth/callback`; `/conta` já tem conteúdo, veja "Conta (`features/account`)"; as demais ainda estão vazias).
- `src/features/<feature>/` — uma pasta por funcionalidade (`editor`, `pricing`, `designs`, `compare`, `auth`, `account`, `workload`, `export`, `legal`). Uma feature só importa outra pelo `index.ts`. O motor de preço (`pricing/{application,model}`) é TypeScript puro, sem React, React Flow nem `fetch`. `pricing/model/catalog.ts` guarda o contrato do catálogo de preços (schemas zod do arquivo de preço e do `manifest.json`, `CATALOG_LIMITS` e tipos); regras em `docs/architecture/aws-cost-playground/price-catalog.md`. `pricing/application/loadCatalog.ts` expõe `createCatalogLoader(read)` (carga do manifest e dos arquivos pedidos, com `sha256` conferido antes do parse e `CatalogError` tipado), sobre a porta `ReadPriceFile`; `pricing/api/httpPriceFiles.ts` é o adaptador HTTP (única pasta do `pricing` que usa `fetch`); `pricing/hooks/usePriceCatalog.ts` é o hook do TanStack Query que entrega o catálogo do design (`idle`, `loading`, `error` ou `ready`), apoiado em `catalogServices` (serviços que o design usa) e `createCatalogSession` (um carregador por aplicação, com uma nova tentativa em erro `integrity`). `pricing/application/{formatUsd,costRows,blockCategory}.ts` e `pricing/hooks/useCostView.ts` formatam o dólar, ordenam as linhas de custo e entregam a visão do painel (regras em "Apresentação no painel" de `cost-estimate.md`). `pricing/model/engine.ts` expõe `estimate(design, catalog)`, que devolve o `CostEstimate` (custo mensal por bloco, aresta e total); por ora provisório, com zeros; contrato em `docs/architecture/aws-cost-playground/cost-estimate.md`. `pricing/model/blockContract.ts` guarda o contrato dos blocos e das arestas (schemas de `contracts/blocks.json` e `contracts/edges.json`, a lista dos 20 tipos e a assinatura da função de preço); `pricing/model/blockRegistry.ts` expõe o registro dos blocos (`BLOCKS`, `blockDefinition`, `blockPricer`, `edgeKindsFor`), com os 20 blocos do PRD em `contracts/blocks.json` e as funções de preço provisórias em `pricing/model/blocks/`; regras em `docs/architecture/aws-cost-playground/block-contract.md`. Os 3 cenários de referência (`contracts/scenarios/`) são conferidos contra esse contrato por `pricing/application/referenceScenarios.test.ts`; veja `docs/scenarios.md`. O lint que cobra essas fronteiras (`eslint-plugin-boundaries` + `no-restricted-imports`) já está ativo desde o PR #88; veja "Lint de arquitetura".
- Store do editor (`features/editor`): `useDesignStore` (Zustand) guarda `document` (o `DesignDocument`), `layout` (posição por id de bloco, fora do documento e do JSON exportado) e `selection`. Os painéis leem com seletor (`useDesignStore((s) => s.document.blocks)`) e escrevem só pelas ações: `addBlock`, `moveBlock`, `removeBlock`, `editBlock`, `connect`, `removeEdge`, `setUsage`, `setOverride`, `select`, `setRegion`, `loadDesign` e `replaceDocument`. Cada ação devolve `Result<T>`: `{ ok: true, value }` ou `{ ok: false, error: { code } }` (`ActionErrorCode`); recusada, não altera nada, e a frase para o usuário é do painel, não da store. `addBlock` e `connect` geram o id e o devolvem em `value`. A lógica é pura em `model/designActions.ts` (sem React nem Zustand); `hooks/designStore.ts` a liga ao estado e cuida de `layout` e `selection`. Importe `useDesignStore` e os tipos pelo `index.ts`.
- Moldura do editor (`features/editor/ui`): `EditorPage` monta paleta, canvas e uma coluna à direita com abas (`RailTabs`: inspetor, custo, carga) e o `EstimateNotice` (aviso de estimativa, texto em `model/estimateNotice.ts`, estado do catálogo vindo de `usePriceCatalog`). A partir de 1024 px as três áreas ficam lado a lado; abaixo disso a coluna da direita vira folha estreita (`useMediaQuery`, calha de 16 px). O canvas já desenha o design (próximo item). Os painéis da direita ainda são vazios; o conteúdo vem das Issues do painel de custo e da exportação.
- Canvas do editor (`features/editor`, #44 parte 1): `CanvasPanel` é o React Flow controlado pela store: nós e arestas derivam do design e cada gesto vira uma ação (`hooks/canvasHandlers.ts` traduz as mudanças do React Flow em `moveBlock`, `select`, `removeBlock` e `removeEdge`; Delete e Backspace removem; o `client` não é removível nem selecionável). Conectar chama `connect` depois de `checkConnection` (contrato `contracts/edges.json` via `edgeKindsFor`); recusa vira um aviso com o motivo. O canvas aceita o soltar da paleta (`isBlockDrag` no `onDragOver`, `dropBlock` no `onDrop`) e tem botões de zoom e de ajustar à tela. `model/canvasModel.ts` (TypeScript puro) deriva nós e arestas do `document`, do `layout` e da `selection` (`toCanvasNodes`, `toCanvasEdges`), posiciona quem não tem entrada no layout (`defaultLayout`: coluna por profundidade, `client` na última), mapeia as 8 categorias do contrato nas 5 do `DESIGN.md` (`canvasCategory`) e formata o custo (`formatUsd`). `hooks/useCanvasCosts.ts` junta `usePriceCatalog` e `estimate` e entrega o custo mensal por bloco já em texto (`Decimal` não sai do hook). `ui/BlockNode.tsx` é o bloco do `DESIGN.md`, com `aria-label` "serviço, rótulo, categoria, custo por mês"; o rótulo é sempre texto, nunca HTML. Os ícones de `ui/CategoryIcon.tsx` são SVGs próprios (o `lucide-react` não é dependência). O CSS do React Flow (`@xyflow/react/dist/base.css`) vem pelo bundle, com as variáveis `--xy-*` ligadas aos tokens. O jsdom não tem `ResizeObserver` nem `DOMMatrixReadOnly`, que o React Flow exige: `src/test/setup.ts` os simula.
- Paleta e arrasto (`features/editor`): `PalettePanel` lista os 20 blocos em cinco grupos (Computação, Dados, Rede, Segurança, Operação), com busca por nome, tipo ou descrição; a lista e os textos ficam em `model/palette.ts`. Teclado: Tab entra na lista em um único item (roving tabindex); setas e Home/End movem o foco entre itens; Seta para baixo na busca vai ao primeiro item e Seta para cima no primeiro item volta à busca; Esc na busca a limpa; Enter ou Espaço adiciona o bloco (posição em diagonal, de 32 em 32 px, por `nextBlockPosition`). Um `role="status"` anuncia o resultado. Contrato do arrasto (exportado pelo `index.ts`): o item grava só o tipo do bloco (ex.: `aws.ec2`) no MIME `BLOCK_DRAG_MIME` (`application/x-acp-block-type`). O canvas chama `isBlockDrag(e.dataTransfer)` no `onDragOver` e, se verdadeiro, `e.preventDefault()` para liberar o soltar (o navegador esconde o conteúdo durante o arrasto, então só `types` é lido). No `onDrop`, chama `dropBlock(e.dataTransfer, posição, designStore.getState().addBlock)`, que valida o tipo contra o contrato, monta o bloco com `newBlockFor(tipo)` (nome, atributos e uso padrão do contrato) e devolve `false` se o dado for inválido ou a store recusar (ex.: limite de blocos). `readDraggedBlockType` expõe só a leitura e validação do tipo.
- Abrir e baixar design (`features/editor`): `ui/DesignFileActions` na barra de ações abre um `.json` e baixa o design atual como `aws-cost-playground-design.json`. A lógica está em `model/designFile.ts`: tamanho conferido contra `DESIGN_LIMITS.maxDocBytes` (350 KB) antes de ler, erro em cinco categorias com frase fixa (nada do arquivo vai para a tela) e migração por `schemaVersion`. Regras em `docs/architecture/aws-cost-playground/design-document.md`.
- `src/shared/` — `config/` (schema e carga do `/config.json`), `lib/design/`, `lib/api/` e `ui/` (tokens e estilo base, veja abaixo). `lib/design/` guarda o contrato do documento do design: schema zod, tipos, limites (`DESIGN_LIMITS`) e `effectiveUsage`. Fica em `shared` porque várias features o usam. Importe pelo `index.ts`. Regras de validação: `docs/architecture/aws-cost-playground/design-document.md`. `lib/api/` guarda as portas da API do SPA (`DesignsApi`, `EstimatesApi`, `QuotaApi`, `AccountApi`, agregadas em `Api`), os DTOs com schema zod e o `ApiError` (discriminado por `kind`, com o guard `isApiError`). É só contrato, TypeScript puro: sem `fetch`, sem React. O cliente HTTP (`shared/lib/http`, #51) e o fake em memória (`lib/api/inMemoryApi.ts`, #151 e #152, fora do `index.ts` para não ir ao bundle de produção) implementam essas interfaces. O fake devolve a `Api` inteira: `DesignsApi` (`update` com `expectedVersion`, que dá `version-conflict` sem gravar, e `duplicate` incluídos), `EstimatesApi`, `QuotaApi` e `AccountApi`. Em testes, importe de `./inMemoryApi` e passe os limites do ADR: `createInMemoryApi({ maxDesigns, maxDocBytes, userDailyLimit, globalDailyLimit })` (20 e 300 por dia), com `now` e `newId` opcionais para dados determinísticos. `llmEnabled` (padrão `true`; `false` dá `unavailable` sem gastar quota) e `estimate` (função injetável; o retorno é revalidado por `estimateResponseSchema`, e resposta fora do schema dá `invalid-response` sem gastar quota) controlam a estimativa. A janela da quota é o dia UTC de `now()` e `resetsAt` é a próxima meia-noite UTC. `estimateUsage` checa nesta ordem: `invalid-request`, `unavailable`, `quota-exhausted` do usuário, `quota-exhausted` global; só então consome os dois contadores. `quota.get()` não consome e não mostra o contador global. `deleteAccount` apaga os designs e zera a quota do usuário, não a global. Os métodos não recebem `userId`: a identidade vem só do JWT. `lib/money.ts` guarda dinheiro e quantidades sem ponto flutuante: `Decimal` é um `bigint` escalado em 10^-12 USD, com `decimal`, `add`, `sub`, `mul`, `div`, `compare`, `sum` e `toFixed`. `decimal`, `mul` e `div` arredondam meio-para-par na 12ª casa. Entrada inválida (não finita, fora do formato, mais de 64 caracteres ou expoente além de ±40) e divisão por zero lançam `RangeError`. `Decimal` não entra em JSON nem em estado persistido; sai por `toFixed`.
- `src/test/` — setup dos testes (Vitest + Testing Library).

## Transporte HTTP (`shared/lib/http`)

- `lib/http/` é o transporte HTTP (#182, parte 1 da #51): `createHttpTransport({ baseUrl, getAccessToken, timeoutMs? })` devolve `request(req, schema)`, que valida a resposta com o schema zod da chamada. Importe pelo `index.ts`.
- Todo erro sai como `ApiError`, só com `kind` e mensagem fixa (sem `cause`, sem texto do servidor).
- O token vem de `getAccessToken`, chamado a cada requisição, e não é guardado nem logado; vai só para a origem de `baseUrl`.
- O tempo limite é de 30 s e a resposta tem teto de 512 KiB. Mapa de status para `kind` e decisões em `docs/handoff/51.md`.
- `createHttpApi(transport): Api` (`lib/http/httpApi.ts`, #184, parte 2 da #51) implementa as interfaces de `lib/api/` sobre o transporte.
- O `ApiProvider({ api, children })` e o hook `useApi()` (`lib/api/ApiProvider.tsx`, #185, parte 3 da #51) entregam a `Api` às telas; `useApi()` lança erro explícito fora do provider. Não é reexportado pelo `index.ts`: importe de `shared/lib/api/ApiProvider`. O `createApi` de `app/bootstrap.tsx` escolhe a implementação: em desenvolvimento (`import.meta.env.DEV`) o fake em memória, carregado por `import()` dinâmico, com os limites do ADR; em produção sempre `createHttpApi`, e o build não leva o fake (`tooling/apiBundle.build.test.ts`). Sem `/config.json` válido o app mostra a tela de erro em qualquer modo, sem cair no fake (falha fechada). O token entra por `bootstrap(container, fetchFn, { getAccessToken })`, ponto de injeção da sessão (#52); o padrão devolve `null` e as chamadas dão `unauthenticated` sem tocar a rede. No `main.tsx`: `bootstrap(container, fetch, { getAccessToken })`.
- Rotas, iguais às do backend (`api/app/*/router.py`, #201): `designs.list` `GET /designs`; `get` `GET /designs/{id}`; `create` `POST /designs` (409 = `design-limit`); `update` `PATCH /designs/{id}` (409 = `version-conflict`); `duplicate` `POST /designs/{id}/duplicate` (409 = `design-limit`); `remove` `DELETE /designs/{id}`; `estimates.estimateUsage` `POST /estimates`; `quota.get` `GET /quota`; `account.deleteAccount` `DELETE /me`.
- A entrada é validada com os schemas de `lib/api/ports.ts` antes de sair: inválida dá `invalid-request` sem chamada de rede, só os campos do contrato vão no corpo e nenhuma identidade é enviada. Id que não passa em `designIdSchema` não vira requisição: `get`, `update` e `duplicate` dão `not-found`; `remove` resolve.
- A listagem aceita no máximo `MAX_DESIGNS` (50, ADR-0001).
- A suíte de paridade em `httpApi.test.ts` roda os mesmos casos contra `createInMemoryApi` e `createHttpApi` (servidor MSW).

## Tokens e estilo base

- `src/shared/ui/tokens.css` é cópia literal dos blocos `css` do `DESIGN.md` (raiz do repositório), a fonte da verdade visual. Os nomes e valores dos tokens não se inventam aqui.
- Para mudar um token, edite o `DESIGN.md` e o `tokens.css` juntos, no mesmo PR. O teste `src/shared/ui/tokens.test.ts` compara os dois nos dois sentidos e falha se divergirem.
- O Prettier ignora o `tokens.css` (`.prettierignore`) para não reformatar a cópia; não o formate à mão.
- `base.css` (estilo base) e `global.css` (importa tokens e base) ficam em `src/shared/ui/`; o `global.css` é importado em `src/main.tsx`. Componentes usam `var(--token)`, sem cores ou medidas fixas.
- `public/theme.js` escolhe o tema antes da primeira pintura: script clássico no `<head>` de `index.html`, sem `defer` e nunca inline (a CSP não ganha `unsafe-inline`). Grava `data-theme` (`light` ou `dark`) no `<html>` a partir de `localStorage['acp-theme']` ou de `prefers-color-scheme`. Fica em `public/`, então o Vite o copia para `dist/theme.js` sem hash e sem passar pelo bundler; o hosting deve servi-lo com `Cache-Control` curto. Regra completa em "Como o tema é escolhido" no `DESIGN.md`.
- `fonts.css` declara 10 `@font-face` (IBM Plex Sans 400/500/600 e Mono 400/500, subconjuntos latin e latin-ext, só woff2, `font-display: swap`, `unicode-range` do `unicode.json` do pacote). Os arquivos vêm de `@fontsource/ibm-plex-sans` e `@fontsource/ibm-plex-mono` (versão exata) e saem em `dist/assets`; nenhuma fonte vem de CDN. `tooling/fontLicenses.ts` emite a licença SIL OFL 1.1 de cada pacote em `dist/fonts/OFL-*.txt`.
- O build proíbe URI `data:`: `build.assetsInlineLimit: 0` e o plugin `tooling/noDataUri.ts`, que falha o build se um chunk ou asset de texto contiver `data:<tipo>/<subtipo>[;,]`. Assim a CSP não precisa liberar `data:`.

## Componentes de `shared/ui` e testes de acessibilidade

- `Button` e `IconButton` (`Button.tsx` + `Button.module.css`) seguem "Botões" e "Estados" do `DESIGN.md`. Variantes `primary`, `secondary` (padrão), `tertiary` e `destructive`; o `IconButton` não tem a terciária e exige `aria-label` (erro de tipo sem ele), que também vira o tooltip. `type` é `button` por padrão. Não aceitam `className` nem `style`: o visual vem só dos tokens. O texto entra como filho React, nunca como HTML.
- `Panel` (`Panel.tsx` + `Panel.module.css`) é o bloco "Section" do `DESIGN.md`: uma região rotulada pelo próprio título (`headingLevel` 2 a 4, padrão 2), com `font-variant-numeric: tabular-nums` em todo o conteúdo. Não aceita `className` nem `style`.
- `TextField`, `NumberField` e `SelectField` (+ `Field.module.css`) seguem "Campos" e "Estados" do `DESIGN.md` e usam a estrutura comum de `Field.tsx` (`Field` e `useFieldControl`, fora do `index.ts`): `<label>` visível acima, que é o nome acessível (o placeholder nunca o substitui); `error` é uma frase com ícone decorativo, ligada por `aria-describedby` e `aria-invalid`; `density` `panel` (padrão, `--control-height`) ou `form` (`--control-height-form`); desabilitado usa `--raised`, `--border` e `--faint`, e o motivo vai em `title`. O `NumberField` é um `<input type="text">` com algarismos tabulares e `inputMode` `decimal` (padrão) ou `numeric`: o valor é texto e a validação fica com a feature; a `unit` aparece dentro da caixa, à direita, em `--faint`, e entra na descrição acessível; clicar em qualquer ponto da caixa (unidade ou margem) foca o input. O `SelectField` é um `<select>` nativo com as opções como filhos `<option>` e seta SVG decorativa. O erro não é anunciado sozinho (sem `role="alert"`): a feature que valida decide quando mostrá-lo e leva o foco ao primeiro campo inválido. Não aceitam `className` nem `style`.
- `Notice` (`Notice.tsx` + `Notice.module.css`) é o aviso do `DESIGN.md`: `tone` `negative`, `warning` ou `neutral` e `message` (uma frase em `string`, nunca HTML). O papel ARIA segue o tom: `alert` no erro, `status` no aviso, `note` no neutro. Um `status` só é anunciado quando a frase muda com o aviso já montado; o que precisa ser ouvido ao aparecer é erro (`alert`). O ícone tem forma própria por tom (a cor não é o único sinal) e nome acessível `Erro` ou `Atenção` no erro e no aviso; no neutro o ícone é decorativo (`aria-hidden`). O fundo e o texto vêm do par `--pill-*` do tom. A frase é texto próprio da interface, escolhido pela feature, nunca `error.message`, detalhe do servidor nem texto da LLM; o aviso não tem ação nem botão de fechar. Não aceita `className` nem `style`.
- `EmptyState` (`EmptyState.tsx` + `EmptyState.module.css`) é o estado vazio: `title`, `description` e `action` (obrigatória), com contorno tracejado de 1px em `--control`. O título é um cabeçalho `headingLevel` 2 a 4 (padrão 3), escolhido pela feature conforme a hierarquia da página. O vazio sempre mostra a próxima ação (um `Button` passado pela feature); título e frase são texto próprio da interface, como no `Notice`. Não aceita `className` nem `style`.
- `ToastProvider` e `useToast` (`Toast.tsx` + `Toast.module.css`): o provider envolve a aplicação e renderiza, depois dos filhos, a caixa do toast no canto inferior esquerdo (flutuante: `--shadow-float`, `--radius-card`; no escuro, `--raised` com borda `--border`), com largura máxima de `--sidebar-width` menos `--space-4`, para ficar sobre a paleta e não cobrir o zoom e o minimapa da folha. `useToast().show(mensagem)` mostra uma frase de tom neutro, que é texto próprio da interface (nunca HTML, `error.message`, detalhe do servidor nem texto da LLM) e curta, de uma linha ("Link copiado."; o ARN fica onde foi copiado, porque uma frase longa vira uma coluna alta sobre a paleta); um toast por vez: o novo substitui o atual e reinicia o tempo. `useToast` fora do provider lança erro. A região `role="status"` fica sempre montada e contém só o texto; o botão de fechar (`IconButton` "Fechar mensagem") fica fora dela. O toast não move o foco, fecha com Esc quando o foco está dentro e, ao fechar com o foco dentro, devolve o foco a quem o tinha antes (elemento HTML ou SVG, como uma aresta do canvas). Some depois de 5 s (`TOAST_DURATION_MS`); o tempo para enquanto o ponteiro está em cima ou o foco está dentro e recomeça inteiro depois. Só a entrada anima (`opacity`/`transform` em `--t-ui`); a saída é instantânea, porque a caixa fecha já vazia. Com `prefers-reduced-motion`, a transição é zerada e a caixa aparece direto na posição final. Nunca leve no toast uma informação que só exista nele: erro fica no bloco que falhou (DESIGN.md, "Estados").
- `Dialog` (`Dialog.tsx` + `Dialog.module.css`) é o diálogo modal: `open`, `onClose`, `title` e `children`. Quem o controla é a feature; fechado, não renderiza nada. Aberto, renderiza em portal no `document.body` um scrim fixo em `--scrim` que centra a caixa (flutuante: `--surface`, `--radius-card`, `--shadow-float`, padding `--card-pad`; no escuro, `--raised` com borda `--border`), com largura até `--rail-width` e altura até a tela menos 2 × `--space-4`, rolando por dentro com `overscroll-behavior: contain`. A caixa tem `role="dialog"` e `aria-modal="true"` e é rotulada pelo `h2` do título, que é texto próprio da interface (nunca HTML). Ao abrir, o foco vai para o primeiro controle e ignora o `autoFocus` dos filhos (não use `autoFocus` dentro do diálogo); por isso "Cancelar" vem antes do primário, e numa confirmação destrutiva o foco cai na ação segura. Tab e Shift+Tab circulam dentro, e o foco que escapa por código volta para dentro logo depois (a guarda espera a feature terminar de fechar); não use `tabindex` positivo dentro. Ao fechar, o foco volta ao elemento que o tinha ao abrir, a menos que a feature já o tenha levado a outro lugar ao fechar (no `onClose` ou no botão que fecha, no mesmo handler em que muda `open`; depois de um `await`, feche com `flushSync` antes de mover o foco, ou mova-o num effect depois de fechar); se o disparador saiu da página, a feature decide para onde levar o foco. Esc chama `onClose` (mas não se um filho já deu `preventDefault` no Esc nem durante composição de IME), também quando o controle focado saiu da página ou foi desabilitado e o foco caiu no `body`; a feature fecha mudando `open`. Clique no fundo não fecha nem tira o foco, para não perder um formulário. Não há botão de fechar (X): a feature passa as ações, e ao menos uma fecha. Nenhuma tecla do diálogo chega ao `document` (`stopPropagation` no scrim e, com o foco perdido no `body`, na captura do `window`), então atalhos globais, como o Backspace do React Flow, não agem atrás dele. Um diálogo por vez: dois disputariam o foco. O fundo não recebe `inert` nem trava de rolagem. O diálogo fica acima do toast (mesmo `z-index: 1`, mas vem depois no DOM): retorno dentro do diálogo usa `Notice`, e toast só depois de fechar. Campos dentro do diálogo usam `density="form"` (`--control-height-form`). Só a entrada anima (`opacity`/`transform` em `--t-ui` com `--ease-out`); com `prefers-reduced-motion`, nada anima. Não aceita `className` nem `style`.
- Cada componente usa um CSS Module (`X.module.css`) só com `var(--…)`; um teste por arquivo confere que não há hex nem `px` literal.
- `src/test/axe.ts` exporta `expectNoAxeViolations(elemento)`, que roda o `axe-core` (versão exata, devDependency) e falha com a lista de violações. A regra `color-contrast` fica desligada: o jsdom não calcula cores, e o contraste dos pares de tokens já está verificado no `DESIGN.md`. Todo componente de `shared/ui` tem um teste que o usa, além do teste de teclado.

## Autenticação (`features/auth`)

Existem o serviço de sessão, em TypeScript puro (sem React, React Flow nem `fetch` na camada `application`), e o provedor do Cognito completo (#262 e #286): descoberta OIDC, início do login, retorno, renovação e logout. A ligação ao app (#263 e #299) tem provedor React, rota de retorno, proteção de rotas e os controles de entrar e sair na barra do editor.

- **Ligação ao app**: o bootstrap cria o serviço (`createBrowserAuth`) e o injeta em `AuthProvider`; as telas leem o estado com `useAuth()`. O `getAccessToken` do transporte HTTP vem do serviço de sessão. `/auth/callback` (`AuthCallbackPage`) conclui o login e mostra os estados carregando e erro. `RequireAuth` protege `/designs` e `/conta`: anônimo é enviado ao login e volta ao destino original (via `safeReturnTo`).
- **Controles na barra do editor** (`ui/AuthActions.tsx`, com o `SignInButton`, compostos em `app/router.tsx` junto de `SaveControls`): anônimo vê Entrar e Criar conta (o botão mostra "Abrindo…" enquanto o login é preparado); autenticado vê o e-mail, com link para `/conta`, e Sair.
- **Design em edição durante o login** (`editor/model/designDraft.ts`, `editor/hooks/designDraftSync.ts`): como a ida ao login recarrega a página, `keepDesignForLogin` guarda o design no `sessionStorage` (chave `aws-cost-playground:design-draft`) antes de sair, se ele tem conteúdo. `useRestoreDesignDraft` o devolve na volta: uso único, vale 30 minutos e só entra num editor vazio, nunca por cima do que já está na tela.
- **Cache por usuário** (`app/sessionCache.ts`): o cache do TanStack Query é limpo ao entrar, sair ou trocar de usuário, para que dados de uma conta nunca apareçam em outra.

- **Portas** (`application/ports.ts`): `IdentityProvider` (login gerenciado: `beginSignIn`, `completeSignIn`, `refresh`, `endSession`), `SessionStore` (`read`, `write`, `clear`; nenhum método lança) e `Navigate` (navegação de página inteira). `createAuthService({ provider, store, navigate, now? })` junta as três; criá-lo não faz chamada de rede.
- **Sessão só em memória** (`infrastructure/memorySessionStore.ts`): os tokens nunca vão para `localStorage`, `sessionStorage`, IndexedDB nem cookie, para que um XSS não os leve embora. O custo é que recarregar a página encerra a sessão local; entrar de novo é rápido porque o login gerenciado do Cognito mantém o próprio cookie. A interface só enxerga `AuthSnapshot` (anônimo ou autenticado com o usuário), nunca os tokens; o snapshot tem referência estável (`useSyncExternalStore`).
- **Renovação**: `getAccessToken()` devolve `null` ao anônimo, o token atual se ainda vale e, senão, renova com o refresh token, com uma única chamada em voo (chamadas concorrentes compartilham a mesma promise). Refresh recusado ou resposta inválida encerra a sessão; falha de rede rejeita com `AuthError('network')` e mantém a sessão. Uma renovação que termina depois de um `signOut` ou de um novo login é descartada.
- **`safeReturnTo`** (`model/returnTo.ts`): o destino pós-login só é aceito se for um caminho interno (uma `/` inicial, até 512 caracteres, sem `\` nem caractere de controle, mesma origem e fora de `/auth/`); qualquer outra coisa vira `/`. Passa por ele na ida (`signIn`) e na volta (`completeSignIn`). Uma mesma `callbackUrl` é processada uma única vez.
- **`signOut`** limpa a sessão local (e o que estava em voo) antes de navegar para o encerramento no provedor, e nunca rejeita; se o provedor falhar, navega para `/`.
- `crypto.getRandomValues` e SHA-256 do PKCE ficam em `infrastructure/webCrypto.ts`.
- **Provedor do Cognito** (`infrastructure/cognitoProvider.ts`, `createCognitoProvider`): Authorization Code + PKCE S256 com `fetch` e Web Crypto. `beginSignIn` descobre os endpoints, gera `state`, `nonce` e `code_verifier`, guarda a tentativa e devolve a URL da tela pedida (`sign-in`, `sign-up` ou `forgot-password`); não navega. `completeSignIn` consome a tentativa (uso único), confere `error`, `code` e `state` da `callbackUrl` (parâmetro repetido, formato ou `state` divergente/expirado são recusados) e troca o código com `code_verifier` no endpoint de token; o ID token precisa ter `iss`, `aud`, `nonce` e `exp` válidos (a assinatura não é verificada no cliente; quem autoriza é o API Gateway) e dele saem só `sub` e o e-mail verificado. `refresh` usa o refresh token (recusa 4xx vira `session-expired`; resposta inesperada, `invalid-response`; 5xx/429, `network`) e mantém o refresh token anterior se o Cognito não enviar outro. `endSession` revoga o refresh token em melhor esforço e devolve a URL de logout (ou `/` se a descoberta falhar). Cada chamada sai sem cookie, sem seguir redirecionamento, sem cache e com tempo limite (10 s); falha vira `AuthError('network')`.
- **Descoberta OIDC** (`model/endpoints.ts`): parte só do `cognitoAuthority` do `/config.json` (`<authority>/.well-known/openid-configuration`), nunca de query. O documento é validado com zod: `issuer` igual ao emissor configurado, S256 suportado quando listado, e todo endpoint `https` e da mesma origem do de autorização; qualquer desvio é `AuthError('invalid-response')`. Sem revogação ou logout no documento, usam-se `/oauth2/revoke` e `/logout` da origem validada; `/signup` e `/forgotPassword` saem dela também. O resultado fica em cache na promise e uma falha não é cacheada.
- **Tentativa de login** (`infrastructure/sessionAttemptStore.ts`): é, com o rascunho do design acima, o que se guarda no `sessionStorage` (chave `aws-cost-playground:login-attempt`), e nunca um token: só `state`, `code_verifier`, `nonce`, destino e hora. Uma por aba (um novo pedido substitui a anterior), de uso único (`take` apaga) e validada por schema; armazenamento bloqueado ou corrompido não lança, e `beginSignIn` rejeita se não consegue guardar.

## Designs salvos (`features/designs`)

Parte 1 da #56: salvar o design atual e mostrar o estado do salvamento.

- **Injeção pelo app**: `SaveControls` (botão "Salvar" e pílula de estado) não é importado pelo editor; o app o passa à `EditorPage` pela prop `actions` (`router.tsx`), que o renderiza na `ActionBar`. A feature `editor` não conhece `designs`.
- **Estado do salvamento** é a função pura `saveStatus(atual, salvo, saving)` em `model/saveState.ts`: `saving` > `unsaved` (nunca salvo) > `saved` (documento igual ao salvo, comparado por `sameDocument`, sem depender da ordem das chaves) > `dirty`. Não é guardado: deriva do documento do editor e do último salvo. `hasUnsavedChanges` serve a quem for sair ou trocar de design.
- **`savedDesignStore`** (Zustand, um por aba) guarda o que o servidor devolveu (`saved`: `id`, `name`, `version`, `doc`), além de `saving` e do tipo do último erro. `begin()` reserva o salvamento e devolve `false` se já há um em andamento, evitando salvamento duplo. Mensagens de erro são texto próprio da interface (`model/designMessages.ts`), nunca o detalhe do servidor.

## Conta (`features/account`)

Nível `clean`. `/conta` fica atrás de `RequireAuth` e a página é `AccountPage` (#58).

- **Conteúdo**: o e-mail da sessão, a quota de estimativas ("Restam N de M", com a data de renovação; lida por `GET /quota`, que não consome, com "Tentar de novo" em erro) e a exclusão da conta.
- **Exclusão** (`DeleteAccountDialog`): diálogo de confirmação em que o botão só habilita depois de digitar a palavra `EXCLUIR`. O foco abre em "Cancelar" (comportamento do `Dialog`).
- **Fluxo** (`application/deleteAccount.ts`, ligado por `hooks/useAccount.ts`): chama `DELETE /me` e, só depois do 204, na ordem: apaga o rascunho do design no `sessionStorage` (`discardDesignDraft`), esquece o design salvo (`forgetSavedDesign`), navega para `/` com `flushSync` (a página sai do DOM antes de a sessão cair, senão a rota protegida levaria ao login), limpa o cache do TanStack Query e chama `signOut`.
- **Erro**: qualquer falha do `DELETE /me` mostra mensagem fixa (`model/accountMessages.ts`, nunca texto da API) e não executa nenhum passo acima; a conta nunca aparece como excluída sem o 204. Tentar de novo é escolha do usuário (sem `retry` automático).
