## Como o workflow funciona (parte 2)

- Só `workflow_dispatch`, com a entrada `sha`. Dois jobs: `check` (sem Environment, sem credencial AWS) e `deploy` (`environment: production`, OIDC).
- **SHA passou por staging:** `find-staging-release.sh` pede à API os runs de `deploy-staging.yml` com aquele `head_sha`. O `release_gate.py` exige run de `push` em `main`, concluído com sucesso, e o job `deploy (staging)` e o passo `Smoke test` com `conclusion: success`. Run verde com o deploy pulado (staging sem `AWS_APPLY_ROLE_ARN`) deixa o smoke `skipped` e é recusado.
- **Mesmo artefato:** os dois jobs baixam `release-<sha>` pelo `run-id` do run de staging e nada é reconstruído. O `check` registra o hash do `SHA256SUMS`, e o `deploy` só aceita esse hash. Os dois consultam o run de novo depois do download e exigem o mesmo run e a mesma tentativa (`run_attempt`). O zip vai para `functions/<sha>.zip` sem sobrescrever, e as funções só passam com o `CodeSha256` desse zip.
- **Preços:** `site/prices/manifest.json` do artefato precisa de `source: price-list`.
- **Smoke:** `scripts/smoke-test.sh`, que também compara o `/prices/manifest.json` servido com o do release.

## Decisões tomadas sem humano

1. **Fatiamento em duas partes** (#319 e #320), porque o total passou de 800 linhas. Descartado: cortar testes para caber.
2. **O deploy de produção roda o mesmo passo de Terraform de staging** (plan, plan-guard e aplicação do plano salvo), agora em `infra/envs/production`. É assim que staging troca o código das funções (`package_key`); trocar o código por fora do Terraform deixaria o estado divergente. O workflow só roda por disparo humano. Não cria recurso nem custo novo.
3. **O Terraform aplicado é o do SHA publicado** (segundo checkout em `release-src/`), e as ferramentas (release-gate, plan-guard, smoke) são as do commit do disparo. Descartado: Terraform do `HEAD`, que aplicaria em produção infraestrutura que staging não viu com aquele código. Consequência: rollback para um SHA cujo Terraform apagaria recursos mais novos é barrado pelo plan-guard, e o runbook manda fazer por `git revert`.
4. **Prova de staging pela API de runs e jobs**, pelos nomes `deploy (staging)` e `Smoke test`. O teste do workflow trava esses nomes em `deploy-staging.yml`. Descartado: marcador gravado no bucket de staging, que exigiria permissão e recurso novos.
5. **`source` aceito por lista fechada** (`price-list`): qualquer outro valor é recusado, não só `seed`.
6. **Produção falha fechada sem configuração.** Staging avisa e termina verde; produção não.
7. **Os passos de publicação repetem o shell de staging** em vez de extrair um script comum, para não alterar `deploy-staging.yml` de carona. O teste compara os blocos dos dois workflows. A extração ficou na #321.
8. **O smoke de staging continua embutido**; a troca pelo `scripts/smoke-test.sh` também está na #321.
