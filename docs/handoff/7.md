## Mangum vs Lambda Web Adapter (checagem de 2026-11-23)

| | Mangum 0.22.0 | AWS Lambda Web Adapter 1.1.0 |
|---|---|---|
| Manutenção | Não arquivado. 3 releases em 12 meses (a última em 2026-08-22). Um único mantenedor ativo, com 19 dos 21 commits humanos. 29 issues abertas. | Org AWS. 4 releases em 12 meses (a última em 2026-09-18). Dois mantenedores principais e mais 11 contribuidores. 4 issues abertas. |
| Distribuição | Wheel `py3-none-any` no PyPI, com hash no `uv.lock` e attestation PEP 740 do workflow do projeto | Binário Rust (275 crates) em layer da conta AWS 753240598075 ou na imagem ECR. Fica fora do lockfile, sem attestation nem SBOM no release |
| O que entra na cadeia | 1 pacote, sem transitiva nova (`typing-extensions` já estava na árvore) | A layer, mais uvicorn e click no PyPI e uma referência de layer cross-account no Terraform |
| Identidade | Evento original em `scope["aws.event"]` | Contexto do authorizer no cabeçalho `x-amzn-request-context` |

O LWA é mais bem mantido. O Mangum ganha em supply chain: tudo fica no lock, com hash e auditado, e a identidade não é lida de cabeçalho. O risco do Mangum é ter um só mantenedor. Ele fica contido porque o adapter só aparece em `main.py` (`create_handler`) e na leitura do evento em `auth.py`. Trocar depois significa mexer nesses dois pontos e na Issue de infra. As issues abertas do Mangum que importam aqui não afetam este uso:

- #342: o lifespan roda a cada invocação, e aqui ele está `off`.
- #302 e #307: host errado atrás de CloudFront, mas a API fica atrás do API Gateway.

## Auditoria de supply chain (`supply-chain-risk-auditor`, 2026-11-23)

- **Escopo:** 12 diretas (6 de runtime, 6 de dev) e 50 transitivas. O pacote de runtime da Lambda soma 30.
- **Advisories na versão exata:** nenhum em OSV, GitHub Advisory DB e PyPI.
- **Fontes do lock:** as 62 vêm do registry `pypi.org/simple`, e os 535 artefatos têm sha256 que confere com o PyPI. Não há git, path nem índice alternativo. Nada yanked, arquivado nem deprecated.
- **Wheels:** nenhum pacote é só sdist, e todos têm wheel para Linux x86_64 e aarch64. Os nativos de runtime são só jiter e pydantic-core.
- **Achados baixos:**
  - Mangum com um único mantenedor (ver acima).
  - `httpx2-jsfetch`, que só entra com `sys_platform == 'emscripten'` e não chega à Lambda.
  - Metade da árvore sem attestation PEP 740; a integridade fica garantida pelos hashes do lock.
- **Recomendação para a Issue de empacotamento da Lambda:** instalar só wheels (`--no-build` no uv), para nunca cair em build de sdist.

## Passo do `validate` para a `api/` (aplicação humana)

Entra depois do passo do `web/` em `.github/workflows/validate.yml`. A parte 3 acrescenta `pricing/uv.lock` ao `cache-dependency-glob` e o passo do `pricing/`.

```yaml
      - uses: astral-sh/setup-uv@68559e99cc807c1eb7e9238fd43a15bba460eec2 # v10.3.3
        with:
          version: "0.13.8"
          enable-cache: true
          cache-dependency-glob: api/uv.lock
      - name: API — format, lint, tipos, arquitetura e testes
        working-directory: api
        env:
          UV_LOCKED: "1" # todo `uv run` também falha se o lock estiver desatualizado
        run: |
          uv sync --locked
          uv run ruff format --check .
          uv run ruff check .
          uv run mypy app
          uv run lint-imports
          uv run pytest -q --cov
```

O uv instala o Python 3.14 a partir de `api/.python-version`.
