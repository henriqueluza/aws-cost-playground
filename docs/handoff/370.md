# Handoff — Issue #370: origem do login gerenciado e `http` só em desenvolvimento

## Estado

Implementado em um PR (`Closes #370`). Achados WEB-1 e WEB-2 de `docs/security/revisao.md`; decisão 23 do autor (26/11/2026).

## O que mudou

- **Regra de host do login (`web/src/features/auth/model/endpoints.ts`, `isLoginOfSite`).** O `authorization_endpoint` da descoberta OIDC só vale se for `https`, sem credenciais, na porta padrão e com host exatamente igual a `auth.` + o host do site. Vale para os dois ambientes porque `infra/modules/dns` monta `auth.${site_domain}`: produção é `<domínio>` e `auth.<domínio>`; staging é `staging.<domínio>` e `auth.staging.<domínio>`. A comparação é de host inteiro, depois de normalizado pelo `URL` (minúsculas, punycode, IPv4) e sem o ponto final do FQDN; não há `endsWith` nem `includes`. Site aberto por IP não tem login. A função é pura: a origem do site entra por parâmetro (`createBrowserAuth` passa `location.origin`).
- **Demais endpoints.** Token, revogação e logout continuam presos à origem do endpoint de autorização, e `/signup` e `/forgotPassword` saem dela; agora essa origem é a do login do site.
- **Erro.** `AuthError('login-origin')`, com frase própria em `authMessages.ts`; aparece nos estados de erro que o login já tinha (diálogo da barra, `RequireAuth`, retorno). Nenhuma URL vai para a mensagem. A tentativa de login não é guardada e o logout volta ao próprio site.
- **Exceção de desenvolvimento.** Com `import.meta.env.DEV` e o site em `localhost`/`127.0.0.1`, o login pode estar em `localhost`/`127.0.0.1` (ainda `https`, pelo schema da descoberta). Fora do servidor de desenvolvimento a opção é `false`.
- **`runtimeConfig.ts`.** O ramo `http` em `localhost` só entra no schema com `import.meta.env.DEV`. O build de produção recusa qualquer `http` em `apiBaseUrl` e `cognitoAuthority`.
- **e2e.** Roda contra o build de produção sem nenhuma exceção: `e2e/support/siteConfig.ts` serve um `/config.json` `https` fictício, e o login simulado fica em `https://auth.localhost` (a regra de produção aplicada ao host `localhost` do `vite preview`). `runtime-config.e2e.ts` prova no bundle de produção que `http://` (inclusive o `public/config.json` que vai no build) dá a tela de erro.

## Decisões tomadas sem humano

1. **Sem modo de build de teste.** Em vez de uma variável de build que reabrisse `http` para o e2e, os testes passaram a servir configuração `https`. O bundle testado é o mesmo que vai ao ar.
2. **`vite preview` com o `public/config.json` mostra a tela de erro.** É consequência direta do critério 2; está no `web/README.md`.
3. **Erro com categoria própria (`login-origin`)** em vez de reutilizar `invalid-response`: o texto "tente de novo" não ajudaria, e o caso é distinguível em teste.
4. **Ponto final do FQDN é normalizado, não recusado** (`auth.exemplo.com.` é o mesmo host no DNS). A CSP do site ainda bloquearia a troca de token nesse host: falha fechada.
5. **A exceção de desenvolvimento não aceita `http` no login.** O schema da descoberta já exigia `https` em todos os endpoints e isso não mudou.
6. **A label `agent:authorized`** não foi conferida na Issue: a autorização é a decisão 23 do arquivo de decisões do autor.
7. **Frase nova de erro sem o protocolo de design completo:** é um texto em um estado de erro existente, sem componente, estilo nem layout novos.
