## Forma do contrato

- `contracts/blocks.json`: `{ schemaVersion: 1, blocks: [{ type, name, category, level, attributes: [{ key, options, default? }], usage: [{ key, unit, default, min, max, integer }] }] }`.
- `contracts/edges.json`: `{ schemaVersion: 1, kinds: [{ kind, usage: [...], pairs: [{ sources, targets }] }] }`; `targets` aceita `client` só em `data`.
- Atributo sem `default` é opcional (só o `az`). Toda chave de uso tem faixa, e o padrão fica dentro dela.
- Função de preço: `BlockPricer = (input: { attributes, usage }) => readonly BlockCharge[]`, com `BlockCharge = { sku, quantity: Decimal, charge: 'fixed' | 'variable' }`. O bloco diz quanto de cada SKU; o motor (#26) aplica faixas, franquia e mínimo.
- Os JSON são a fonte única; o `web/` os importa por caminho relativo e valida com zod na carga (#176). A API (#10) lê os mesmos arquivos.

## Decisões tomadas sem humano

O PRD lista os 20 blocos, os níveis e os tipos de aresta, mas não traz os atributos nem as chaves de uso de cada bloco, nem a matriz de pares das arestas. O que foi decidido, sempre pela leitura mais conservadora:

| Decisão | Alternativa descartada | Motivo |
| --- | --- | --- |
| Dados em `contracts/*.json` na raiz, importados pelo `web/` por caminho relativo | Definição em TypeScript com JSON gerado | A #9 e a #10 pedem fonte única em `contracts/`, lida também pela API em Python. `tsc`, ESLint, build e o servidor de desenvolvimento do Vite aceitam o import sem mudar configuração |
| Atributos e chaves de uso derivados do exemplo do ADR-0001 (Lambda e S3) e dos critérios das Issues de preço #30 a #42 | Esperar o autor listar parâmetro por parâmetro | Bloquearia o gargalo do projeto; é dado, ajustável por PR. As tabelas completas estão nos corpos da #176 e da #177 |
| Conjuntos fechados pequenos (ex.: S3 só `STANDARD` e `STANDARD_IA`; 11 tipos de EC2; RDS só `postgres` e `mysql`) | Conjuntos amplos | Acrescentar opção depois é compatível; remover não é. Menos SKUs no catálogo ajuda a meta de ±15% |
| `az` com opções `a`, `b`, `c`, sem padrão | Nome completo da AZ (`us-east-1a`) | O design tem uma região e o custo entre AZs só compara igualdade; a letra serve para as duas regiões |
| CloudFront sem chave de transferência no bloco | `dataTransferGbPerMonth` no bloco | O egress vem da aresta `data` para `client` (ADR, "uso por aresta"); duas fontes contariam em dobro |
| Blocos de custo por hora sem `hoursPerMonth`, exceto EC2 | Horas em todos | Só a #33 (EC2) pede horas por mês; os demais assumem o mês inteiro |
| Um bloco NAT Gateway = um gateway; um bloco RDS = uma instância | Chave de quantidade | As Issues #34 e #36 não pedem quantidade |
| CloudTrail com `trails` + `managementEventsPerMonth` + `dataEventsPerMonth` | Chave "eventos pagos" | Modela "além da primeira trilha" (#40) sem pedir à LLM um número já descontado |
| Aresta `data` entre os 15 blocos de tráfego; IAM, CloudFormation, CloudWatch, CloudTrail e CodePipeline não levam `data` | Qualquer par; ou matriz par a par | O PRD não dá a matriz. Regra simples, em dado, que não recusa arquitetura comum |
| Destino `client` só a partir de CloudFront, S3, ALB e EC2 | Incluir NAT Gateway | ADR-0001, "Fluxo da estimativa de carga" |
| `logs` de qualquer bloco (menos o CloudWatch) para o CloudWatch | Lista de quem emite log | PRD F4: "`logs` (bloco para CloudWatch)" |
| Sem rótulo de UI no contrato; `unit` e `name` em inglês | `label` em pt-BR por chave | Texto de interface é da UI (#48); a API não precisa dele |
| Regras de par (`runs-on` só ECS para EC2 etc.) ficam no JSON e são fixadas por teste do arquivo, não por `refine` no schema | Repetir a regra no schema | O schema valida a forma; duplicar o dado no código criaria uma segunda fonte |
| Assinatura da função de preço definida aqui | Deixar para a #26 | A #9 exige função provisória por bloco; a #26 pode estender a entrada |
| Regex de chave duplicada de `shared/lib/design` | Exportar `fieldKey` de lá | Evita mudança de carona no contrato do design |

## Pontos de atenção para quem consome

- **#10 / #61 (API):** o zip da Lambda precisa incluir `contracts/`. As regras de validação do schema zod (padrão dentro da faixa, `integer`, nível igual ao do PRD) valem para o leitor em Pydantic.
- **#26 (motor):** o design aceita qualquer `usage` de 0 a 1e12; quem limita à faixa do contrato antes do cálculo é o motor (ou o inspetor, #48). Não há função de `clamp` nesta entrega.
- **#28 (catálogo):** sugestão de convenção, não imposta em código: `service` do arquivo de preço = tipo do bloco sem o prefixo `aws.` (17 serviços com preço = 20 blocos menos os 3 de nível C).
- **#32 (DynamoDB) e #40 (CodePipeline):** as chaves de uso dos dois modos convivem no bloco; a função de preço ignora as do modo que não está selecionado.
- **Formatação dos JSON:** à mão, uma linha por atributo e por chave de uso.
