## Divergências conhecidas zod × Pydantic

Sondagem diferencial em 26/11: 163 documentos crus (chave repetida, coerção, números de borda, Unicode, datas, `__proto__`, raiz e listas de tipo errado) passaram pelo zod (`JSON.parse` + `safeParse`) e pelo Pydantic (`json.loads` + `model_validate` e `model_validate_json`). A única diferença de veredito foi o substituto solto. Os casos que nenhum exemplo fixava viraram arquivo: `valid/duplicate-keys-last-wins`, `valid/numbers-float-edge-cases`, `valid/fields-32-keys-plus-proto`, `invalid/duplicate-key-last-invalid`, `invalid/usage-value-overflows-float`, `invalid/estimated-at-no-seconds`, `invalid/label-number`.

- Substituto UTF-16 solto: o zod aceita, a API recusa.
- Números de 1e-6 até antes de 1e-5: o JS escreve `0.000001` e o Pydantic `1e-6`; o `sizeBytes` calculado na API fica alguns bytes menor. Os outros números saem com o mesmo tamanho (conferido com inteiro acima de 64 bits, `1e308`, `-0`, `1e-7`).
- `NaN`/`Infinity` no JSON: o `JSON.parse` recusa o arquivo, o `json.loads` aceita e o modelo recusa depois. Os dois lados dão inválido.
- `loc` de erro em atributo traz nomes de ramo da união do Pydantic (`constrained-str` etc.). O veredito não muda.
- A lista de erros: o zod relata todos; o Pydantic para no primeiro bloco e na primeira aresta inválidos (`fail_fast`).
